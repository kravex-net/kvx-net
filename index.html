Move indices between Elasticsearch and OpenSearch.

Kravex is a command-line tool that streams documents from one cluster to another through the bulk API. It watches how the destination is coping and adjusts batch size as it goes. Elasticsearch 5–8 and OpenSearch 1–3, in either direction.

git clone https://github.com/kravex-net/kravex
cd kravex
cargo run --release -p kvx-cli -- kvx.toml

How it works

You describe a source and a destination in a TOML file and run the binary with the file as its only argument. OpenSearch goes through the same Elasticsearch backend, because both speak the same bulk API. Moving from Elasticsearch to OpenSearch is a matter of changing a URL.

# kvx.toml
[source_config.Elasticsearch]
url   = "http://localhost:9200"
index = "employees"

[sink_config.Elasticsearch]
url   = "http://localhost:9201"   # an OpenSearch cluster works here too
index = "employees"
cargo run --release -p kvx-cli -- kvx.toml

What it does while it runs

  • Adapts batch size to the destination. It backs off when the cluster returns 429s and ramps back up when it recovers. Pick a fixed size, a throughput-seeking mode, or a latency or CPU-targeting controller in the [governor] section.
  • Doesn't trust a 200. The bulk API returns 200 even when individual documents are rejected. Kravex reads the response body, and retries the documents that failed.
  • Retries with backoff. Retry count and backoff are configurable under [drainer].
  • Authenticates with basic auth or an API key.

What it doesn't do yet

  • It copies documents only. Create the destination index, with its mappings and settings, before you start. Kravex doesn't migrate mappings, settings or templates.
  • There is no checkpoint file, so an interrupted run can't pick up where it stopped.
  • You build it from source, which needs a Rust toolchain.
  • The version range above comes from the project README. The repo's own Docker setup exercises Elasticsearch 8.15 and OpenSearch 2.19.

Numbers

One dataset, one laptop. This is the Rally geonames corpus: 11,396,503 documents, about 3.5 GB of JSON. Elasticsearch and OpenSearch ran in Docker Desktop on an M1 Pro, with the destination limited to 2 cores and 4 GiB of memory.

DestinationDocumentsTimeDocs / minPeak memory
Elasticsearch 8.1511,396,5038 min1.43 M135 MB
OpenSearch 2.1911,396,5039.5 min1.19 M135 MB

Fixed-size batches. Document counts matched the source. The destination's two cores were the limit, so a larger cluster should go faster. Don't read these as a promise for your data, because document size, mappings and hardware change everything. The harness is in the repo's demo/ directory, and you can run it yourself.

Alternatives

You have options for moving index data, and several are good at what they were built for. This is where each one tends to stop short for a large index-to-index move. Every claim links to its source, and these tools change, so check before you decide.

Elasticdump Reports of about 1 GB/hour in a community thread, and single-index reads go through the scroll API. Thread · Issue #11
Logstash Elastic's write-up of moving a billion log lines saw throughput fall from about 6,000 to 700 docs/sec as pagination got deeper. Blog post
Reindex API Runs inside the destination cluster. For a remote source, the destination must be able to reach it and the host must be allowlisted. Docs
AWS Migration Assistant Runs on an AWS stack (CloudFormation, ECS, MSK, S3) and targets OpenSearch only. Aimed at live capture of up to about 4 TB/day. Docs
Airbyte General-purpose data movement. Elasticsearch is a destination connector, and pricing is based on volume. Connector · Pricing
